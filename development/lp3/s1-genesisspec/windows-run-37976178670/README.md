## The 16 BLOCKED BY PLATFORM rows

**Cause, one for all 16:**

- `tests/lp3_genesis_cli.py` (lines 34–38) uses an OS address-space limit only when `resource.RLIMIT_AS` and `os.wait4` exist.
- CPython on Windows has no `resource` module. So each check that needs a limit is reported as BLOCKED BY PLATFORM (lines 146–148), not run, and never counted as passed.
- The verification script adds one summary row for the same reason.

**Expected beforehand:** this is the classification designed in round 2 and predicted in `../author-r4-encoding-fix/README.md`. The Linux run of the harness's Windows code path predicted PASS 2 / BLOCKED 7 for debug and PASS 2 / BLOCKED 8 for release-max. Windows produced exactly that.

**Overlap:** the 16 rows are 8 distinct cases.

- **Summary row:** 1 row, `RLIMIT_AS address-space limit checks`, which restates the other 15 and is not a separate test.

- **Release-only case:** 1 row, `gsVersion2818466Bytes`, which exists only with `--max-version`.

## Other observations from the logs

None of these changes a result. I found no failure and no implementation defect. No change was made, because any change to the script or harnesses would alter the tested tree and need another Windows run.

1. **Line endings at checkout.** For 46 of 52 files, the Windows working-tree hashes in `source-hashes.json` differ from the git blob hashes. All 46 equal the blob after LF→CRLF conversion, which is Git for Windows checkout conversion.
   - The other 6 are fixture JSON files that git already stores with CRLF; they are unchanged.
   - `.gitattributes` (`/development/m1/** -text`) protects the M1 inputs, so their hashes equal the blobs.
   - Windows therefore built and tested exactly the commit's content, with CRLF line endings in the crate sources. `check_evidence.py` verifies every file.
2. **`environment.json` reports `rustup`'s active rustc as 1.99.0.**
   - The script runs `rustup --version` (script line 224) before it installs 1.58.1 and sets `RUSTUP_TOOLCHAIN` for later child processes (lines 228–230). The 1.99.0 is therefore the runner's default toolchain.
   - Every later step ran 1.58.1: `rustc -vV` reports 1.58.1, `cargo -V` reports 1.58.0, and cargo printed the old `Finished dev [unoptimized + debuginfo]` format.
   - Proposed correction (cosmetic): record `rustup --version` after the toolchain is selected, or label the field "runner default".
3. **The detail of the two CLI parent rows is `{`.**
   - The script keeps the first line of the harness's indented JSON. The same happened in the Linux smoke runs.
   - The full output is in `artifact/logs/lp3-genesis-cli*.log` and `artifact/lp3-genesis-cli*.json`.
   - Proposed correction: put the harness's `statuses` (for example `PASS 2, BLOCKED BY PLATFORM 7`) in the detail.
4. **Runner time.** The run took 54 minutes; on Linux with Python 3.13, the same two release-max steps took about 30 s and 66 s. The heavy steps:
   - `lp3-genesis-cli-release-max` took 903.2 s, although its two executed sub-checks took 0.05 s and 0.02 s.
   - `lp3-genesis-diff-release-max` took 1862.31 s.

   The cause is Python 3.11, which the workflow pins. It converts an integer to a decimal string in quadratic time.
   - The CLI harness computes the expected 6,787,543-digit decimal (line 214) before `check()` reports that case BLOCKED.
   - The differential computes the reference's decimal for two full-size items, which is required work.

   Measured in this container for a 262144-byte value: Python 3.11.17 took 5.97 s, Python 3.13.16 took 0.47 s. For the full 2,818,466-byte value, 3.13.16 took 6.04 s and 3.11.17 took 707.78 s (`python-str-int-timing-linux.txt`; a Linux measurement, not Windows). About 15 runner minutes, billed at the Windows rate on this private repository, went to a check that could not run.
   - Proposed correction: in `lp3_genesis_cli.py`, skip computing `want` when no limit is available.
   - Optionally, run the harnesses on Python ≥ 3.12. The workflow pins 3.11, the version the M1 root used (`../author-r1/README.md`), so changing it is an owner decision.
